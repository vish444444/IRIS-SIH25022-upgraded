# AI_MODEL.md — Delay Prediction Model

## Honesty notice

This model is trained **entirely on synthetic data** generated by
`ai-service/data/generate_dataset.py`. It is not trained on, and does not
claim to reflect, real Indian Railways operational data. It exists to
demonstrate a genuine, working ML pipeline (data generation ->
feature engineering -> training -> evaluation -> inference API) inside
the decision-support architecture, and to feed realistic-shaped
features into the conflict/optimization layers for the demo.

## Model

- **Type:** `sklearn.ensemble.GradientBoostingRegressor`
- **Why not XGBoost/LightGBM:** avoids an extra native dependency in the
  demo environment while remaining a boosted-tree model with the same
  interpretability (`feature_importances_`) and comparable behaviour.
- **Target:** `future_delay_min` — predicted delay (minutes) at the next
  station/section, given the train's current state.

## Features (13)

`current_delay_min, train_type_code, priority, current_speed_kmh,
previous_speed_kmh, dwell_time_sec, distance_to_next_km,
section_occupancy, trains_ahead, congestion_index, platform_available,
disruption_active, scheduled_headway_sec`

`congestion_index` is itself a deterministic formula (see
`features/feature_engineering.py::compute_congestion_index`), not a
learned value — it's a model **input**, not a second model.

## Synthetic data generator

`data/generate_dataset.py` builds rows from 8 named, documented
scenario templates (NORMAL, MINOR_DELAY, HEAVY_DELAY, CONGESTION,
BREAKDOWN, TRACK_BLOCKAGE, PLATFORM_CONFLICT, SIGNAL_RESTRICTION), each
with its own distribution over the input features, then computes the
target via a hand-written, documented formula
(`compute_future_delay`) plus Gaussian noise. This means the model is
demonstrably learning the structure we deliberately injected — it is
disclosed as such, not presented as a predictive breakthrough on real
data.

## How to (re)train

```bash
cd ai-service
python3 -m venv .venv && source .venv/bin/activate   # optional
pip install -r requirements.txt
python3 training/train_model.py --rows 8000
python3 training/evaluate_model.py --rows 2000 --seed 999   # holdout check
```

Outputs: `models/delay_model.joblib`, `models/metrics.json`,
`models/feature_columns.json`.

## Actual measured metrics (real, not fabricated)

Measured by running the commands above in this repository:

| Split | Rows | MAE (min) | RMSE (min) | R² |
|---|---|---|---|---|
| Test split (20% of 8,000 training rows, seed 42) | 1,600 | 2.072 | 3.544 | 0.961 |
| Independent holdout (2,000 rows, different seed=999) | 2,000 | 2.172 | 3.586 | 0.961 |

The close agreement between the in-training test split and the fully
independent holdout (different random seed, regenerated from scratch)
indicates the model generalizes across the synthetic distribution
rather than overfitting to one draw — expected, since both are drawn
from the same documented generator.

## Top feature importances (from the trained model)

Re-run `python3 training/train_model.py` and inspect
`models/metrics.json -> feature_importances` for the exact values;
`disruption_active`, `congestion_index`, and `current_delay_min`
dominate, which matches the injected formula in
`compute_future_delay` — a useful sanity check that the model learned
the intended structure.

## Inference API

`POST /ai/predict-delay` (FastAPI) — see API.md for the schema. The
Node backend does not call this directly; it is available for the
frontend/what-if flows and is exercised by
`ai-service/tests/test_delay_model.py`.

## Known limitations

- Not validated against any real railway dataset (none was available).
- The formula-driven target means the "ceiling" R² is a property of the
  chosen noise level in `compute_future_delay`, not an inherent property
  of real-world delay predictability.
- Congestion is a deterministic feature, not a separately-trained
  "congestion prediction" model, despite being listed as a sub-module in
  the original architecture sketch — this is disclosed rather than
  implemented as a second black-box model, since a second model trained
  on the same synthetic generator would not add genuine signal.
